# 禅道工时日志填报（Excel → 禅道）

用户写好一张 Excel，本 skill 负责解析、校验、dry-run 展示、确认后写入禅道，并回查验证。

**核心链路：**

```
本机 python  --(ssh -L 隧道)-->  跳板机(公司 VPN)  -->  禅道
```

不需要在跳板机上跑 PowerShell、不需要 PowerShell 处理中文编码。所有逻辑在本机跑，禅道侧只是被隧道穿透的 HTTPS。

## 为什么不用「跳板机 PowerShell」方案

旧方案是「写 .ps1 → scp 到跳板机 → powershell -File」，用来绕开 Windows 跳板机没有 curl 的限制。
如果跳板机允许 SSH 端口转发，直接 `ssh -L` 把禅道映射到本机即可 —— 本机有 python、原生 UTF-8，
PowerShell 的 GBK 乱码、CRLF、只读自动变量等坑全部不需要。

## 环境依赖

| 项 | 值 |
|---|---|
| 本机 python | `python`（3.9+，需要 `openpyxl`） |
| 凭证 | `~/.zentao-credentials.env`（`ZT_USERNAME` / `ZT_PASSWORD`），可用 `ZT_CRED` 覆盖路径 |
| SSH 跳板机 | `~/.ssh/config` 里的别名，默认 `jumpbox`；`ZT_JUMPBOX` 留空则直连 |
| 禅道 | `https://zentao.example.com`（占位符，改成自己的域名） |

前置条件：**跳板机可登录、公司 VPN 在线**。掉线时的表现和恢复方式见 `reference/chandao-api.md`。

## Excel 格式

模板：`templates/禅道工时填报.xlsx`（数据区留空，示例只放在「填写说明」页，避免误提交）

| 列 | 必填 | 说明 |
|---|---|---|
| 日期 | 否 | `YYYY-MM-DD` / `2026/1/15` / `1.15` / `今天` / `昨天`，留空 = 今天 |
| 类型 | 否 | `task` / `bug`（有下拉）。留空则从对象号猜 |
| 对象号 | **是** | `123456`、`任务#123456`、`BUG#123456`、`task_123456` 都认 |
| 工作内容 | **是** | 原样存进禅道「工作」字段，中文随意 |
| 消耗工时 | **是** | 小时，必须 > 0（禅道拒绝 0） |
| 剩余工时 | 否 | **留空最好**，脚本自动算「该任务当前剩余 − 本次消耗」；同一任务多行按提交顺序**累计扣减**。手填 = 你说了算（绝对值，覆盖任务当前值）。写 `0` = 把任务置为完成（见红线） |
| 测试包版本 | 条件 | 仅当「剩余工时 = 0」时必填，格式**用等号**：`example-pkg=1.0.0-1` |

表头顺序随意，允许在前面加标题行（脚本会在前 10 行内自动定位表头）；模板自带的「说明行」会被自动跳过。`对象号` 或 `工作内容` 以 `#` 开头的行会被当注释跳过。

## 标准工作流

设 `ZT` 为脚本路径（在本 skill 目录下）：

```bash
ZT="scripts/zt.py"
```

### 1. 确认链路 + 拿任务号（读，安全）

```bash
python "$ZT" whoami          # 显示当前登录账号
python "$ZT" tunnel          # 只想探隧道时用
python "$ZT" tasks           # 列我的任务：ID/状态/已耗/剩余/执行/名称
python "$ZT" tasks 关键词     # 按关键词过滤
```

不用先手动开隧道 —— 每个子命令都会自己 `ensure_tunnel()`。
**隧道不跨命令常驻**（沙箱会连带回收 ssh 子进程），每次调用自动重建，约 1~2s，属正常开销。

用户说「不知道任务号」时，用 `tasks` 查给他，别让他去网页翻。

### 2. dry-run 看计划（读，安全）

```bash
python "$ZT" plan "C:/path/to/填报.xlsx"
```

输出每行的解析结果、计算后的剩余工时、`[置为DONE]` 标记，以及**全部校验错误**。有错误时退出码 2，必须先修 Excel。**这一步绝不写数据。**

### 3. 确认后写入（写）

```bash
python "$ZT" submit "C:/path/to/填报.xlsx" --yes
```

不带 `--yes` 只打印计划、不写。写入后自动做三件事：

1. **记台账**（并校验确实落盘，没落盘会红字警告）；
2. **回读校验**：以禅道侧真实数值为准，逐条比对任务「已耗 / 剩余」，不符会标 `!!`；
3. 回查当日工时记录列表。

> **成功响应 ≠ 数值落对。** 必须看回读校验那一段，尤其是「剩余」这一列。

### 4. 单独回查

```bash
python "$ZT" verify 2026-01-15     # 或省略日期=今天
```

## 红线（必须遵守）

1. **先 plan 再 submit。** 永远不要在没给用户看过 dry-run 计划的情况下直接 `--yes`。
2. **`left[1]` 必须发，且它是「绝对值」。** 部分实例校验「日期N : 剩余不能为空」——**不发 left 整条表单被拒**（HTTP 仍 200）。
   语义是把任务的「预计剩余」**赋**成这个值（实测：发 25 就落 25）。脚本按「当前剩余 − 本次消耗」自动算，同一任务多行累计扣减；你在 Excel 里手填则覆盖。
3. **HTTP 200 + 响应里出现 `"success"` 不等于写进去了。** 禅道的 AJAX 外壳恒为 `{"status":"success","data":"…"}`，
   真正的业务结果在 `data` 里（如 `{"message":"日期1 : 剩余不能为空。"}`）。**判定必须穿透外壳**（`_judge()` 已做），
   而且**每次都要回读「已耗」**才知道真相（曾因此整批 4 条静默失败）。
4. **禅道有删除入口，但部分实例的工时被外部工时系统同步接管。** 网页上有 `/effort-delete-{id}.html` 和 `/effort-edit-{id}.html`，
   但通过接口更新工时会返回 `{"result":"fail","message":"同步工时-更新的禅道工时数据不存在,请检查"}`
   —— 说明这条工时同步到外部工时系统了，**别用脚本改/删已有工时**，让用户去网页处理。这也是要有 dry-run 和台账的原因。
5. **`剩余工时 = 0` 会把任务置为「完成」**，且此时禅道强制要求 `testPackageVersion`。只有用户明确要交付/关闭时才这么填。
6. **禅道不保证采纳你发的 left。** 实测连续写入时，偶尔会出现只落了 `consumed`、left 停在旧值的情况。
   提交成功不代表 left 落对 —— 回读那一段会用 `!!` 标出来，并按需提示用户去 `task-edit-{id}.html` 手工改。
7. **台账去重**：已提交的行记在 `.ledger/YYYY-MM.csv`（**按月一个文件**，跨月也要读全），重复的行默认跳过并在计划里标 `[台账已有→跳过]`。确需重填加 `--force`。
   **只有判定为成功的行才入台账**；失败行不入账，这样修好原因后可以安全重跑。
8. **不要把 `--yes` 当成默认动作**。用户说「填吧」也要先 plan。

## 已知坑（都是实测，别再踩）

| 现象 | 原因 / 对策 |
|---|---|
| **4 条全说 OK，回读才发现一条没写进去** | 失败藏在 AJAX 外壳的 `data` 里（`{"status":"success","data":"{…剩余不能为空…}"}`）。`_judge()` 已改为穿透 `data` 判定；并且回读会比对任务「已耗」 |
| `日期1 : 剩余不能为空。` | 部分实例要求 `left[n]` 必填。脚本现在恒发 left（绝对值） |
| 任务「预计剩余」被写成离谱大数 | 历史事故：那次发 left 时**没带 `execution`**。现已同时带 `execution[n]`，left 按实测语义落值 |
| 同一任务多行，剩余算错 | 剩余是累计扣减；被台账跳过（不提交）的行**不能**推进累计基准。`build_plan` 已按此处理 |
| `alert('对象为任务时执行不能为空！')` | 部分实例的同步插件要求带 `execution`。脚本已按任务自动带上 `execution[n]` |
| `{"result":"fail","message":"同步工时-…"}` | 工时已同步到外部工时系统，接口改不动，只能网页处理 |
| 提交「失败」但实际写进去了 | 成功时返回 `<script>if(parent!==window) parent.location.reload(true);</script>`，不是 JSON |
| 回查 0 条 | `/effort-ajaxGetEfforts-{uid}-{ym}.json` 在部分实例返回 `[]`（不可用）。改用 `/my-effort.json`（分页 JSON，`data` 里是转义字符串，首页 20 条） |
| 判定数值异常看哪里 | `GET /task-view-{id}.html` 含**完整变更历史**（「修改了 预计剩余，旧值为…新值为…」），一眼定位 |
| 日期 `9.16` 报格式错 | Excel 把它存成了数字 9.16。`norm_date()` 现在按「月.日」解释，也支持 Excel 日期序列号 |
| 模板第 2 行「说明行」被当成数据 | `_is_legend()` 命中 2 个以上模板提示词就整行跳过 |

## 出问题时的排查顺序

1. `zt.py tunnel` 报「隧道 20s 内未就绪」或任务时报 `CONNERR` → 跳板机的 **VPN 掉了**，让用户重连 VPN 后重试。
2. 登录报错但隧道通 → 查 `~/.zentao-credentials.env` 里 `ZT_USERNAME` / `ZT_PASSWORD` 是否有效（改过密码会失效），以及 `ZT_REALM` 是否与实例匹配。
3. 提交报 FAIL → 看 `<-` 后的中文消息（那是从 AJAX 外壳 `data` 里解出来的业务原因），常见是对象号不存在、`consumed` 为 0、`left` 缺失、或 `left=0` 却没给 `testPackageVersion`。
4. 提交报 OK 但**回读的「已耗」没涨** → 别信判定，去 `GET /task-view-{id}.html` 搜「记录工时」看变更历史；没出现就是真没写进去，修掉原因后重跑（失败行不入台账，可安全重跑）。**注意 `/my-effort.json` 首页只有 20 条**，按日期筛选时可能是漏的。
5. 中文变问号/乱码 → 检查是不是有人把 `zt.py` 的表单提交改成了手拼 `%XX`。脚本用的 `urlencode(encoding="utf-8")` 是正确的，不要动。
